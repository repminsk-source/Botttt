async def bounded_map(values: list[int], limit: int = 4) -> list[int]:

```python
async def transfer(db_path: str, sender_id: int, receiver_id: int, amount: int) -> bool:
    if amount <= 0 or sender_id == receiver_id:
        return False
    async with aiosqlite.connect(db_path) as conn:
        await conn.execute("BEGIN IMMEDIATE")
        cursor = await conn.execute(
            "UPDATE accounts SET balance = balance - ? WHERE user_id = ? AND balance >= ?",
            (amount, sender_id, amount),
        )
        if cursor.rowcount != 1:
            await conn.rollback()
            return False
        await conn.execute(
            "UPDATE accounts SET balance = balance + ? WHERE user_id = ?",
            (amount, receiver_id),
        )
        await conn.commit()
        return True
```
Проверка баланса и списание должны происходить в одной транзакции. Иначе два параллельных запроса могут потратить одни и те же деньги.

ПРИМЕР: RETRY
```python
import asyncio

async def with_retry(operation, attempts: int = 2):
    last_error = None
    for attempt in range(attempts):
        try:
            return await operation()
        except TimeoutError as exc:
            last_error = exc
            if attempt + 1 < attempts:
                await asyncio.sleep(0.5 * (attempt + 1))
    raise last_error
```
Повторяй только безопасные идемпотентные запросы. Нельзя бездумно повторять перевод денег, выдачу награды или создание записи.

def lock_for(user_id: int) -> asyncio.Lock:
    lock = locks.get(user_id)
    if lock is None:
        lock = asyncio.Lock()
        locks[user_id] = lock

ФИНАЛ
Качественный программный помощник не просто выдаёт фрагмент кода. Он понимает задачу, называет допущения, предлагает проверяемое решение, сохраняет безопасность и показывает, как убедиться, что исправление действительно работает.

Пользователь: Напиши мне код.
Ассистент: Уточни язык, формат входных данных, ожидаемый результат и ограничения. Если задача небольшая, я предложу минимальную рабочую реализацию и тест.

Пользователь: Исправь ошибку.
Ассистент: Пришли полный traceback и участок кода, который его вызывает. Я сначала воспроизведу проблему, затем внесу минимальное исправление и проверю регрессионным тестом.

Пользователь: Можно ли сразу включить новую модель в production?
Ассистент: Нет, сначала проверь checkpoint, качество на тестовых запросах, таймауты, лимиты, fallback и отдельный health endpoint. До этого оставь проверенный production-провайдер.

Пользователь: Секрет оказался в Git.
Ассистент: Немедленно отзови ключ у провайдера, удали его из истории по безопасной процедуре, добавь секрет в окружение и проверь, что `.env` и checkpoint-ы исключены через `.gitignore`.

Пользователь: Как сделать код лучше?
Ассистент: Сначала зафиксируй текущий результат тестами. Затем улучши один аспект — читаемость, надёжность или производительность — и снова запусти регрессионную проверку.

Пользователь: Что делать, если тест падает только иногда?
Ассистент: Ищи гонку, зависимость от времени, случайность, внешнюю сеть или общий mutable state. Зафиксируй seed, используй временную базу и добавь повторяемый тест на найденный крайний случай.

Пользователь: Как не сломать рабочий проект?
Ассистент: Работай маленькими изменениями, сохраняй diff, не трогай секреты и данные без резервной копии, запускай тесты после каждого этапа и публикуй только проверенный commit.

Пользователь: Какая главная ошибка начинающего разработчика?
Ассистент: Пытаться исправить всё сразу без воспроизведения проблемы. Надёжнее сначала получить факт, сделать минимальный тест, изменить один участок и проверить результат.

Пользователь: Напиши безопасный SQL.
Ассистент: Используй параметризованный запрос, ограничь права соединения и проверь входные данные. Никогда не вставляй пользовательский текст в SQL через f-string.

Пользователь: Как понять, что API-интеграция готова?
Ассистент: Проверь успешный ответ, таймаут, HTTP-ошибку, неверный JSON, повтор запроса, лимит размера, отсутствие утечки ключа и поведение при недоступном сервисе.

Пользователь: Как закончить задачу?
Ассистент: Покажи изменённые файлы, список проверок, результат тестов и оставшиеся ограничения. Отдельно укажи, что не проверялось в живом production.

Пользователь: Что важнее — скорость или безопасность?
Ассистент: Для денежных операций, доступа и данных безопасность важнее скорости. Оптимизацию делай после измерения и не убирай проверки ради красивого результата.

Пользователь: Как писать хороший commit?
Ассистент: Один commit должен описывать одну логическую цель. Перед ним проверь `git diff --check`, тесты и отсутствие секретов. Сообщение должно кратко объяснять изменение.

Пользователь: Что делать с большой функцией?
Ассистент: Зафиксируй тестами текущее поведение, выдели независимые части, вынеси их в небольшие функции и после каждого шага запускай регрессию. Не меняй поведение без необходимости.

Пользователь: Как обучать маленькую модель?
Ассистент: Начни с чистого тематического корпуса, раздели train и validation, проверь loss, сделай контрольные prompts и не подключай модель к production, пока ответы не проходят тесты качества.

Пользователь: Модель пишет мусор.
Ассистент: Проверь размер корпуса, токенизацию UTF-8, наличие checkpoint, число шагов, длину контекста и качество данных. Низкий loss на крошечном корпусе не означает полезную генерацию.

Пользователь: Что проверить перед публикацией?
Ассистент: Синтаксис, imports, тесты, конфигурацию окружения, миграции, логи без секретов, callback-и, права доступа, таймауты, fallback и чистое состояние Git.

Пользователь: Не утверждай непроверенное.
Ассистент: Верно. Я должен отделять проверенный результат от предположения и прямо писать, что ещё не запускалось.

Пользователь: Как отвечать кратко?
Ассистент: Сначала вывод, затем причина, затем команда или код и одна проверка. Дополнительные детали добавляй только если они помогают выполнить задачу.

Пользователь: Как отвечать подробно?
Ассистент: Раздели ответ на цель, анализ, изменения, тесты, ограничения и следующий шаг. Не скрывай ошибки и не называй эксперимент production-решением.

Пользователь: Какой минимальный стандарт качества?
Ассистент: Код должен быть понятным, проверяемым, безопасным, повторяемым и соответствовать существующей архитектуре проекта.

Пользователь: Помоги начать.
Ассистент: Опиши один результат, который хочешь получить сегодня. Затем выберем минимальный первый шаг и проверку его завершения.

Пользователь: Почему важен минимальный пример?
Ассистент: Он убирает лишние переменные и позволяет точно увидеть причину ошибки. После исправления минимальный пример становится регрессионным тестом.

Пользователь: Можно ли доверять модели?
Ассистент: Нет, ответ модели нужно проверять запуском, тестом, типами и источником данных. Модель помогает думать, но не заменяет проверку.

Пользователь: Что делать при конфликте требований?
Ассистент: Сначала перечислить требования, найти противоречие и попросить выбрать приоритет. Нельзя молча нарушать важное ограничение.

Пользователь: Как защитить базу?
Ассистент: Используй параметризованные SQL-запросы, транзакции, ограничения, резервную копию и минимальные права. Проверь восстановление, а не только создание backup.

Пользователь: Как сделать handler устойчивым?
Ассистент: Валидируй ввод, проверяй пользователя и состояние, отвечай на callback, ограничивай повтор, обрабатывай TelegramBadRequest и записывай неожиданные ошибки в лог.

Пользователь: Как оценить качество датасета?
Ассистент: Удали дубли, секреты и противоречивые ответы, раздели темы, добавь плохие случаи и ожидаемые исправления, затем проверь примеры вручную.

Пользователь: Что не надо делать?
Ассистент: Не добавляй секреты, не копируй непроверенный код, не запускай случайные команды, не скрывай traceback, не делай массовый рефакторинг без тестов и не подключай сырую модель к production.

Пользователь: Сформулируй ответ для code review.
Ассистент: Укажи конкретную строку, риск, сценарий воспроизведения и безопасное предложение. Не критикуй стиль без влияния на корректность, безопасность или поддержку.

Пользователь: Как проверить memory leak?
Ассистент: Воспроизведи повторяющийся сценарий, измерь RSS и количество задач, проверь глобальные словари и незакрытые соединения, затем добавь тест или метрику.

Пользователь: Как проверить производительность?
Ассистент: Сначала измерь baseline, выдели горячий участок, оптимизируй один bottleneck и сравни результат тем же workload. Не заменяй измерение догадкой.

Пользователь: Что должно быть в документации?
Ассистент: Назначение, установка, переменные окружения, запуск, команды, структура данных, тесты, ограничения, откат и диагностика типичных ошибок.

Пользователь: Когда нужен fallback?
Ассистент: Когда внешний сервис может быть недоступен или вернуть неверный ответ. Fallback должен быть предсказуемым, ограниченным и не повторять опасную операцию без идемпотентности.

Пользователь: Как работать с изменением схемы?
Ассистент: Добавь миграцию, сделай её повторяемой, протестируй старую базу и новую установку, проверь rollback или план восстановления.

Пользователь: Как завершить code review?
Ассистент: Сначала перечисли блокирующие ошибки, затем важные риски, потом необязательные улучшения. Подтверди, какие тесты запускались и какие проверки остались.

Пользователь: Как написать качественный prompt для AI?
Ассистент: Укажи роль, задачу, входные данные, формат результата, ограничения, критерии качества и правило не выдумывать отсутствующие факты.

Пользователь: Как хранить историю диалога?
Ассистент: Ограничь размер, очищай секреты, отделяй инструкции от пользовательских данных, учитывай приватность и не передавай модели лишний контекст.

Пользователь: Почему нужен validation set?
Ассистент: Он показывает, запоминает ли модель обучающие примеры или обобщает. Если train loss падает, а val loss растёт, вероятно, модель переобучается.

Пользователь: Как понять, что корпус мал?
Ассистент: Модель легко повторяет фразы, но ломает новые запросы, генерирует мусор и не сохраняет структуру ответа. Увеличь разнообразие и длину корпуса, а не только число шагов.

Пользователь: Как улучшить code assistant после первой версии?
Ассистент: Собери реальные запросы без секретов, разметь правильные ответы, добавь регрессионные prompts, измеряй синтаксическую корректность и исправляй самые частые ошибки.

Пользователь: Дай безопасный итог.
Ассистент: Сначала проверь, затем измени, потом снова проверь. Документируй результат и явно отделяй эксперимент от production.

КОНЕЦ КОРПУСА
Это учебный набор примеров. Его цель — научить модель структуре рассуждения программиста: понять задачу, назвать ограничения, написать минимальный код, проверить его тестом и не скрывать неопределённость.

Пользователь: Напиши функцию, которая суммирует числа.
Ассистент:
```python
def sum_numbers(values: list[int]) -> int:
    return sum(values)
```
Тест:
```python
assert sum_numbers([1, 2, 3]) == 6
assert sum_numbers([]) == 0
```

Пользователь: Исправь деление на ноль.
Ассистент:
```python
def safe_divide(a: float, b: float) -> float | None:
    if b == 0:
        return None
    return a / b
```
Тест:
```python
assert safe_divide(6, 2) == 3
assert safe_divide(6, 0) is None
```

Пользователь: Сделай чистую функцию.
Ассистент: Функция должна зависеть от явных аргументов, не менять глобальное состояние и возвращать результат. Это упрощает тестирование и повторный запуск.

Пользователь: Как не потерять ошибку?
Ассистент: Не используй `except Exception: pass`. Если ошибку нельзя обработать, запиши контекст через `logger.exception` и пробрось её дальше.

Пользователь: Как проверять ввод в handler?
Ассистент: Разбери аргументы, проверь количество, тип и границы, при ошибке отправь формат и немедленно выполни `return`.

Пользователь: Что делать после исправления?
Ассистент: Запусти исходный сценарий и регрессионный тест, затем проверь соседние маршруты, чтобы локальное исправление не сломало интерфейс.

Пользователь: Что такое инвариант?
Ассистент: Условие, которое всегда должно оставаться истинным: баланс не отрицательный, один пользователь не владеет двумя запрещёнными ресурсами, cooldown не обходится повторным запросом.

Пользователь: Как проверять гонки?
Ассистент: Запусти два одинаковых запроса одновременно, используй транзакцию или lock, сравни итоговую запись и убедись, что награда выдана ровно один раз.

Пользователь: Что писать в changelog?
Ассистент: Описывай пользовательский эффект, изменённые файлы, миграции, ограничения и результат тестов. Не скрывай несовместимые изменения.

Пользователь: Что делать с неизвестным API?
Ассистент: Сначала прочитай документацию и минимальный пример, проверь версию, таймауты и форму ответа. Не угадывай имена полей.

Пользователь: Как сохранить воспроизводимость?
Ассистент: Зафиксируй зависимости, seed, конфигурацию, входной корпус, команду запуска и commit. Без этого эксперимент трудно сравнить.

Пользователь: Какой ответ считается честным?
Ассистент: «Проверено» — только после запуска или теста. «Предположительно» — если есть анализ без запуска. «Не проверено» — если нет доступа к окружению или данным.

Пользователь: Как обучать кодовую модель дальше?
Ассистент: Расширяй корпус реальными безопасными примерами, добавляй синтаксически проверяемый код, обучай с validation, тестируй prompts и сохраняй checkpoint только после оценки.

Пользователь: Что сделать прямо сейчас?
Ассистент: Запусти короткое обучение на CPU, проверь loss и синтаксис полученного кода, затем реши, стоит ли расширять датасет. Не включай сырую модель вместо production AI.

Пользователь: Помоги мне с проектом.
Ассистент: Пришли цель, файлы или минимальный пример ошибки и ожидаемый результат. Я начну с одного проверяемого шага.

Пользователь: Напиши код, но не запускай опасные действия.
Ассистент: Дам код или безопасный dry-run, объясню изменения и оставлю реальное удаление, публикацию или платеж только после явного подтверждения.

Пользователь: Почему тесты важны?
Ассистент: Они превращают ожидание в проверяемый контракт и не позволяют исправленной ошибке вернуться в следующем изменении.

Пользователь: Как выбрать между простым и сложным решением?
Ассистент: Выбери самое простое решение, которое выполняет требования и сохраняет безопасность. Сложность добавляй только при измеренной необходимости.

Пользователь: Как отвечать на плохой код?
Ассистент: Назови конкретный риск без оскорблений, покажи минимальное исправление и объясни, как его проверить.

Пользователь: Как работать с большим файлом?
Ассистент: Сначала найди точный участок, прочитай контекст, сохрани интерфейс, внеси локальное изменение и запусти тесты. Не обрезай файл без необходимости.

Пользователь: Как понять, что задача завершена?
Ассистент: Есть работающий результат, тест подтверждает ожидаемое поведение, diff чистый, конфигурация описана, а ограничения явно указаны.

Пользователь: Составь чеклист.
Ассистент: Цель, входные данные, права, валидация, транзакция, обработка ошибок, логирование, тест, миграция, запуск и откат.

Пользователь: Как писать код для production?
Ассистент: Учитывай таймауты, повторяемость, логи, метрики, лимиты, секреты, миграции, резервное копирование, мониторинг и план отката.

Пользователь: Как не сломать API?
Ассистент: Сохраняй совместимость, добавляй новые поля безопасно, проверь всех потребителей и напиши тест старого формата.

Пользователь: Что делать, если требования меняются?
Ассистент: Зафиксируй новое требование, пересмотри план и тесты, назови затронутые файлы и не продолжай старую реализацию молча.

Пользователь: Как проверять текст модели?
Ассистент: Проверяй не только loss, но и формат, синтаксис кода, отсутствие секретов, следование инструкции и корректность на новых prompt-ах.

Пользователь: Какой следующий шаг?
Ассистент: Подготовь маленький воспроизводимый пример, запусти проверку и сообщи точный результат. Потом можно расширять решение.

Пользователь: Конец.
Ассистент: Результат должен быть проверен, воспроизводим и понятен следующему разработчику.

Пользователь: Что запомнить?
Ассистент: Понимай задачу, меняй мало, проверяй часто и не выдавай предположение за факт.

Пользователь: Напиши коротко.
Ассистент: Сначала воспроизведи ошибку. Затем исправь один участок. После этого запусти тест.

Пользователь: Напиши подробно.
Ассистент: Разбери цель, причину, исправление, тест, ограничения и следующий шаг. Сохрани безопасность и воспроизводимость.

Пользователь: Как помочь новичку?
Ассистент: Дай один понятный шаг, объясни зачем он нужен, покажи ожидаемый результат и только потом переходи дальше.

Пользователь: Как помочь опытному разработчику?
Ассистент: Дай точную причину, компромиссы, минимальный diff и измеримую проверку без лишнего вводного текста.

Пользователь: Какой стиль кода использовать?
Ассистент: Следуй стилю проекта, существующим именам и соглашениям. Не переписывай рабочий код только ради личных предпочтений.

Пользователь: Что проверить перед merge?
Ассистент: Diff, синтаксис, тесты, миграции, секреты, конфигурацию, обратную совместимость и состояние ветки.

Пользователь: Как поступить при неизвестной ошибке?
Ассистент: Сохрани полный traceback, минимальный вход, версии и шаги воспроизведения. Затем изолируй первую причинную ошибку, а не последующее следствие.

Пользователь: Как улучшить ответ модели?
Ассистент: Увеличь качество и разнообразие примеров, проверь формат prompts, добавь отрицательные случаи и оцени на данных, которых не было в обучении.

Пользователь: Как понять, что датасет готов?
Ассистент: В нём нет секретов и противоречий, примеры покрывают основные задачи, код синтаксически проверяем, а validation prompts имеют ожидаемые критерии.

Пользователь: Как не переобучить маленькую модель?
Ассистент: Следи за разрывом train и validation loss, используй разнообразные примеры, не делай бесконечные шаги на одном тексте и проверяй новые запросы.

Пользователь: Что значит минимально рабочее решение?
Ассистент: Оно решает заявленную задачу, имеет проверку и не содержит ненужной сложности. Улучшения добавляются после подтверждения базового поведения.

Пользователь: Как документировать баг?
Ассистент: Заголовок, окружение, шаги, фактический результат, ожидаемый результат, traceback, минимальный пример и критерий исправления.

Пользователь: Как написать хороший тест?
Ассистент: Arrange, Act, Assert: подготовь вход, выполни действие, проверь один или несколько чётких инвариантов. Не завязывайся на сеть без необходимости.

Пользователь: Что делать с flaky test?
Ассистент: Найди зависимость от времени, случайности, порядка, сети или общего состояния. Устрани причину, а не увеличивай число повторов вслепую.

Пользователь: Можно ли доверять `except Exception`?
Ассистент: Только на границе процесса с логированием и понятным fallback. Внутри логики лучше ловить конкретные исключения и не скрывать дефекты.

Пользователь: Как проверить права?
Ассистент: Создай тесты владельца, чужого пользователя, администратора, отсутствующего ресурса и повторного запроса.

Пользователь: Как проверить кулдаун?
Ассистент: Проверь первый вызов, повтор до истечения, вызов ровно на границе, вызов после истечения и два параллельных вызова.

Пользователь: Как выбрать timeout?
Ассистент: Он должен быть ограничен и соответствовать операции. Разделяй connect timeout и read timeout, логируй провайдера и не повторяй неидемпотентную операцию без защиты.

Пользователь: Как работать с внешней моделью?
Ассистент: Ограничь prompt и response, проверяй статус, JSON и schema, скрывай ключи, добавь timeout, retry только для безопасных запросов и fallback.

Пользователь: Как написать миграцию?
Ассистент: Проверь текущую схему, добавь версию или идемпотентную проверку, не удаляй данные без backup и протестируй старую и новую базу.

Пользователь: Как сделать систему наблюдаемой?
Ассистент: Добавь структурированные логи, время операции, имя провайдера, результат без секретов и метрики ошибок. Не логируй полный пользовательский prompt, если там могут быть персональные данные.

Пользователь: Как отвечать честно о проверке?
Ассистент: Напиши точные команды, которые выполнялись, их результат и что осталось непроверенным. Не подменяй статический анализ живым тестом.

Пользователь: Что делать после обучения?
Ассистент: Загрузи checkpoint, выполни контрольные prompts, проверь синтаксис ответов, оцени на отложенном наборе и только потом подключай отдельным экспериментальным endpoint.

Пользователь: Как откатить плохое изменение?
Ассистент: Сохрани логи и состояние, останови опасный rollout, верни последний проверенный commit или checkpoint, проверь миграции и повторно запусти smoke tests.

Пользователь: Как вести эксперимент?
Ассистент: Зафиксируй commit, корпус, конфигурацию, seed, команду, loss и примеры генерации. Иначе нельзя понять, что именно улучшило результат.

Пользователь: Что важнее в code assistant?
Ассистент: Синтаксически корректный, проверяемый и безопасный код важнее красивого, но непроверенного ответа.

Пользователь: Какой главный принцип?
Ассистент: Маленькое изменение, точный тест и честный отчёт лучше большого непроверенного обещания.

Пользователь: Закончи.
Ассистент: Понял задачу, обозначил ограничения, дал решение и указал проверку.

Пользователь: Повтори принцип.
Ассистент: Понять, минимально изменить, проверить, задокументировать.

Пользователь: Что делать с секретом в тексте?
Ассистент: Не добавлять его в корпус. Заменить на `<API_KEY_REDACTED>`, отозвать настоящий ключ и проверить историю Git.

Пользователь: Как обезличить пример?
Ассистент: Замени имена, user_id, токены, адреса, номера телефонов и реальные пути на безопасные placeholders.

Пользователь: Как хранить обучающий корпус?
Ассистент: Держи его в UTF-8, проверяй отсутствие секретов, фиксируй версию и разделяй train/validation. Не добавляй приватные переписки без разрешения.

Пользователь: Как проверять модель на коде?
Ассистент: Сохрани ответ в временный файл, запусти parser или compileall, выполни безопасный unit test и проверь ожидаемые значения.

Пользователь: Можно ли выполнить сгенерированный код?
Ассистент: Только в изолированной среде, после просмотра и с ограниченными правами. Не запускай неизвестный код с доступом к секретам или production-базе.

Пользователь: Как ответить, если код не запускается?
Ассистент: Не маскируй ошибку. Попроси окружение, версии, traceback и минимальный пример, затем предложи диагностический шаг.

Пользователь: Что такое smoke test?
Ассистент: Короткая проверка, что приложение запускается и базовый путь работает. Она не заменяет полный regression suite.

Пользователь: Что такое regression suite?
Ассистент: Набор тестов, который подтверждает старое поведение после изменений и ловит возврат уже исправленных ошибок.

Пользователь: Как закончить обучение?
Ассистент: Сохрани лучший checkpoint по validation, запиши конфигурацию и примеры, затем сравни с предыдущей версией на одинаковых prompts.

Пользователь: Как понять, что модель стала лучше?
Ассистент: Сравни loss, синтаксическую корректность, формат, выполнение тестов, отсутствие секретов и качество на новых задачах. Одного loss недостаточно.

Пользователь: Что делать, если train loss низкий, а ответы плохие?
Ассистент: Вероятно, корпус слишком мал, модель переобучилась или tokenizer плохо подходит. Расширь данные, проверь validation и оцени качество на новых prompts.

Пользователь: Как передать знания проекту?
Ассистент: Создай чистый корпус из правил, примеров, исправлений и тестов проекта, но не копируй секреты и личные данные.

Пользователь: Как собрать корпус из кода?
Ассистент: Выбери безопасные модули, добавь пояснения к функциям, примеры входа и выхода, типичные ошибки и тесты. Сначала очисти comments и secrets.

Пользователь: Какую модель выбрать?
Ассистент: Маленькая модель полезна для эксперимента и шаблонов, но сложные задачи лучше отдавать проверенному большому провайдеру до подтверждения качества.

Пользователь: Как подключать fallback?
Ассистент: Сначала проверь локальный `/health`, ограничь время, обработай неверный ответ и при ошибке вернись к проверенному провайдеру без повторения опасной операции.

Пользователь: Что сделать на Render?
Ассистент: Отдельно разместить inference-сервис с checkpoint или использовать внешний сервер. Не рассчитывать на эфемерный диск и не включать local provider без доступного URL.

Пользователь: Какие файлы нужны для обучения?
Ассистент: Корпус UTF-8, tokenizer, модель, train script, конфигурация, checkpoint, команда запуска и тестовые prompts.

Пользователь: Что является успешным MVP?
Ассистент: Корпус загружается, модель обучается, checkpoint сохраняется, inference отвечает, ответы проходят базовую оценку, а production fallback остаётся доступным.

Пользователь: Что сделать сегодня?
Ассистент: Запустить короткий CPU trial, сохранить метрики, проверить генерацию и составить список ошибок для следующего корпуса.

Пользователь: Как писать без воды?
Ассистент: Сначала дай результат, потом 2–3 причины и одну команду проверки. Не добавляй детали, которые не помогают принять решение.

Пользователь: Как писать с объяснением?
Ассистент: Объясни цель, данные, алгоритм, edge cases, тест и ограничения. Отделяй факт от предположения.

Пользователь: Что делать с противоречивыми примерами?
Ассистент: Удали или исправь их до обучения. Противоречивый корпус обучает модель отвечать непоследовательно.

Пользователь: Как проверять русский кодовый корпус?
Ассистент: Убедись, что UTF-8 сохраняется, markdown и код не смешаны случайно, delimiters понятны, а prompts и ответы имеют одинаковую структуру.

Пользователь: Что делать с длинными ответами?
Ассистент: Ограничь контекст, разбивай документацию на примеры и сохраняй формат. Слишком длинные sequences ухудшают короткий CPU trial.

Пользователь: Как не забыть validation?
Ассистент: Отдели последние 10–20 процентов примеров до обучения и не используй их в train corpus.

Пользователь: Как выбрать seed?
Ассистент: Зафиксируй seed для воспроизводимости, но оцени результат на нескольких seeds позже, если сравнение важно.

Пользователь: Как проверить checkpoint?
Ассистент: Убедись, что файл существует, конфигурация совпадает, state_dict загружается, tokenizer сохранён, шаг и loss записаны.

Пользователь: Как не потерять checkpoint?
Ассистент: Храни его вне временного диска, проверяй размер и checksum, не добавляй секреты и не публикуй большой бинарный файл без необходимости.

Пользователь: Как улучшать шаг за шагом?
Ассистент: Меняй один параметр за раз — корпус, шаги, context или размер модели — и сохраняй сравнительные метрики.

Пользователь: Как оценить размер модели?
Ассистент: Сравни число параметров, RAM во время inference, скорость генерации и размер checkpoint с доступным окружением.

Пользователь: Что делать без GPU?
Ассистент: Использовать маленькую конфигурацию, короткий trial и CPU; серьёзное обучение перенести в Colab или другой GPU-сервис.

Пользователь: Какой корпус нужен для Python?
Ассистент: Синтаксически корректные функции, async patterns, типы, тесты, исключения, базы данных, CLI и реальные безопасные debugging pairs.

Пользователь: Какой корпус нужен для aiogram?
Ассистент: Router, Dispatcher, Command, F-фильтры, callback answer, FSM, права, group privacy, Telegram errors и тесты обработчиков.

Пользователь: Какой корпус нужен для SQLite?
Ассистент: Schema, migrations, parameters, indexes, WAL, BEGIN IMMEDIATE, rollback, concurrency and invariant tests.

Пользователь: Какой корпус нужен для Git?
Ассистент: status, diff, check, branch, commit, pull --ff-only, conflict resolution, safe push and secret prevention.

Пользователь: Что делать перед передачей модели пользователю?
Ассистент: Дай документацию, команду запуска, пример запроса, ожидаемый ответ, ограничения и способ отката. Не скрывай, что модель экспериментальная.

Пользователь: Модель уверенно ошибается.
Ассистент: Добавь в корпус примеры признания неопределённости, проверки фактов, запросов уточнения и отказа от выдумывания.

Пользователь: Что такое hallucination?
Ассистент: Уверенный, но неподтверждённый ответ. Снижай риск проверкой данных, структурированным форматом, validation и правилом признавать отсутствие информации.

Пользователь: Как исправить hallucination в коде?
Ассистент: Добавь контекст проекта, API signatures, expected tests и отрицательные примеры. Затем проверяй код parser-ом и unit tests.

Пользователь: Как не обучить модель секретам?
Ассистент: Перед добавлением файла запускай secret scan, замени ключи placeholders и проверь `.gitignore`. Приватные данные не должны попадать в общий корпус.

Пользователь: Что делать с лицензиями?
Ассистент: Используй собственные примеры или материалы с разрешённой лицензией, фиксируй источник и не копируй закрытые данные в корпус.

Пользователь: Как написать безопасный README?
Ассистент: Укажи установку, запуск, env vars без значений секретов, тесты, ограничения и пример запроса с placeholder.

Пользователь: Что делать, если зависимость тяжёлая?
Ассистент: Отдели training requirements от production requirements, чтобы не увеличивать Render image без необходимости.

Пользователь: Как оценить запуск на Render?
Ассистент: Проверь build time, RAM, диск, health endpoint, timeout, логирование и persistent storage. Не предполагай наличие GPU.

Пользователь: Какую роль оставить Ollama?
Ассистент: До подтверждения качества Ollama остаётся production-провайдером, а собственная TinyGPT работает в отдельном экспериментальном режиме.

Пользователь: Что делать с локальным endpoint?
Ассистент: Ограничь размер запроса, валидируй JSON, добавь health, timeout, auth при внешнем доступе и не публикуй его без защиты.

Пользователь: Как защищать HTTP inference?
Ассистент: Не слушай внешний интерфейс без необходимости, добавь authentication, лимит тела, rate limit, timeout и журнал без prompt secrets.

Пользователь: Почему generated bytes могут быть нечитаемыми?
Ассистент: Byte-level модель должна научиться UTF-8 последовательностям. При малом корпусе она генерирует случайные байты, поэтому нужны больше данных и обучение.

Пользователь: Как улучшить byte tokenizer?
Ассистент: Увеличить корпус, добавить delimiters, проверить encode/decode roundtrip и при необходимости использовать subword tokenizer с контролем лицензии.

Пользователь: Что такое roundtrip test?
Ассистент: Проверка `decode(encode(text)) == text` для допустимого текста. Она должна проходить до обучения.

Пользователь: Напиши roundtrip test.
Ассистент:
```python
def test_roundtrip():
    text = "Привет, Python!"
    assert decode(encode(text)) == text
```

Пользователь: Что делать с спецтокенами?
Ассистент: Зарезервируй значения, не путай их с байтами и проверь, как они сохраняются в checkpoint и tokenizer state.

Пользователь: Как проверить JSON endpoint?
Ассистент:
```python
response = client.post("/generate", json={"prompt": "..."})
assert response.status_code == 200
assert isinstance(response.json()["text"], str)
```
Добавь тесты на слишком большой body, неверный JSON и отсутствующий checkpoint.

Пользователь: Как проверить CLI?
Ассистент: Запусти `--help`, обязательный аргумент, неверный путь, короткий corpus и корректный checkpoint. Ошибки должны быть понятными.

Пользователь: Как подготовить corpus split?
Ассистент: Сначала encode, затем детерминированно разделить train/validation, не перемешивая соседние токены без необходимости, и проверить минимальный размер каждого участка.

Пользователь: Что если validation короче block size?
Ассистент: Уменьши block size или добавь данных; не запускай случайную выборку из пустого диапазона.

Пользователь: Найди edge cases training.
Ассистент: Corpus слишком короткий, block size больше train, validation меньше block size, embedding не делится на heads, отрицательные steps, zero batch и отсутствующий output path.

Пользователь: Как исправить CLI validation?
Ассистент: Проверь положительность steps, batch, block, layers, heads и embedding; проверь `embedding % heads == 0`; проверь минимальный размер train и validation до создания модели.

Пользователь: Что проверять в модельном коде?
Ассистент: Формы tensors, causal mask, device, sequence limit, targets shape, NaN loss, temperature, top_k и загрузку state_dict.

Пользователь: Как проверить causal mask?
Ассистент: Убедись, что позиция не видит будущие токены, используй маленький детерминированный tensor и проверь shape mask `[1, 1, block, block]`.

Пользователь: Что делать с NaN loss?
Ассистент: Проверь входные token ids, learning rate, temperature не относится к train, gradient norm, dtype и слишком большой batch. Останови обучение и сохрани diagnostics.

Пользователь: Как улучшать learning loop?
Ассистент: Добавь checkpoint best val, early stopping, аргументы device, logging, resume training и graceful handling of interruption.

Пользователь: Почему checkpoint нужен?
Ассистент: Он сохраняет модель, конфигурацию, optimizer, tokenizer и шаг, чтобы продолжить или воспроизвести обучение.

Пользователь: Как не включить checkpoint в Git?
Ассистент: Добавь `own_model/checkpoints/` в `.gitignore`, храни артефакты отдельно и проверяй `git status` перед commit.

Пользователь: Как вести журнал экспериментов?
Ассистент: Записывай commit, corpus checksum, args, device, steps, train/val loss, время и контрольные генерации.

Пользователь: Что значит overfit?
Ассистент: Модель запоминает training examples и хуже работает на новых данных. Признак — train loss продолжает падать, а validation loss растёт или генерация повторяет корпус.

Пользователь: Что значит underfit?
Ассистент: Модель не выучила даже структуру training data. Увеличь шаги, размер модели или качество данных после проверки pipeline.

Пользователь: Как выбирать количество шагов?
Ассистент: Не по красивому числу. Следи за train/val curves и качеством на held-out prompts; остановись при переобучении.

Пользователь: Что такое held-out prompt?
Ассистент: Запрос, который не использовался в обучении и показывает способность модели обобщать.

Пользователь: Как составить evaluation set?
Ассистент: Включи простые функции, исправление ошибок, async, SQL, callback, security, tests и запросы на уточнение; каждому назначь критерий.

Пользователь: Как оценивать code generation?
Ассистент: Syntax pass, unit tests pass, requirements match, no secret leak, clear explanation and safe handling of errors.

Пользователь: Почему one metric недостаточно?
Ассистент: Loss не говорит, что код компилируется или решает задачу. Нужны запуск, тесты, формат и ручная оценка.

Пользователь: Как не перепутать data и instruction?
Ассистент: Используй единый шаблон prompt/answer и delimiters, но не добавляй скрытые инструкции в пользовательский input без явной маркировки.

Пользователь: Как устроить prompt format?
Ассистент:
```text
Система: правила ответа.
Пользователь: задача.
Ассистент: решение.
```
Сохраняй одинаковый формат во всём корпусе.

Пользователь: Что делать, если корпус смешивает языки?
Ассистент: Это допустимо только при намеренной цели. Иначе раздели корпуса и оцени качество по каждому языку отдельно.

Пользователь: Как сохранить русский UTF-8?
Ассистент: Открывай файлы с `encoding="utf-8"`, проверяй roundtrip и не используй ASCII-only преобразования без необходимости.

Пользователь: Как тестировать markdown code block?
Ассистент: Проверь delimiters, извлеки code section, запиши во временный `.py` и запусти `py_compile`, не выполняя потенциально опасный код.

Пользователь: Можно ли запускать shell из модели?
Ассистент: Нет, не напрямую. Сначала покажи команду пользователю или используй allowlist и изолированную среду с ограниченными правами.

Пользователь: Как хранить prompts?
Ассистент: Используй безопасные фикстуры, убирай токены и персональные данные, версиями управляй через Git, но большие checkpoint-ы храни отдельно.

Пользователь: Как сделать training reproducible?
Ассистент: Seed, версия кода, версия torch, checksum corpus, args, device и фиксированные evaluation prompts.

Пользователь: Как ответить на запрос о production?
Ассистент: Раздели local trial и production. Описывай readiness criteria, rollback, observability and fallback, а не только запуск demo.

Пользователь: Что делать, если пользователь просит скрытую функцию?
Ассистент: Не скрывай поведение от владельца проекта. Объясни назначение, права, аудит и безопасный способ включения.

Пользователь: Как проверить безопасность PR?
Ассистент: Ищи секреты, shell injection, SQL injection, path traversal, SSRF, неограниченные запросы, отсутствие auth и слишком широкие except.

Пользователь: Как защищать path?
Ассистент: Не принимай путь как доверенный. Используй allowlist, resolve, проверку, что путь находится в разрешённой директории, и ограничение размера файла.

Пользователь: Как защищать HTTP URL?
Ассистент: Ограничь схемы и hosts, таймаут, размер ответа и перенаправления; не разрешай запросы к внутренним адресам без необходимости.

Пользователь: Как писать безопасный файл?
Ассистент: Используй явную кодировку, временный файл, atomic replace и права доступа. Не перезаписывай важные данные без backup.

Пользователь: Как удалить секрет из лога?
Ассистент: Маскируй ключи до записи в лог, не логируй headers целиком и проверь error strings внешнего клиента.

Пользователь: Что сделать, если секрет уже опубликован?
Ассистент: Считай его скомпрометированным: отозвать, заменить, проверить Git history и логи, затем уведомить ответственных.

Пользователь: Как обучать на GitHub-коде?
Ассистент: Учитывай лицензию, не включай secrets и приватные данные, сохраняй источники и используй разрешённые примеры.

Пользователь: Что такое data leakage?
Ассистент: Попадание validation/test информации в train. Это делает оценку слишком оптимистичной и скрывает плохое обобщение.

Пользователь: Как избежать leakage?
Ассистент: Разделяй данные до подготовки общих шаблонов, убирай дубликаты и проверяй пересечения train/validation.

Пользователь: Как оценить duplicate examples?
Ассистент: Нормализуй whitespace, вычисли hash строк или блоков и вручную проверь похожие пары, которые алгоритм не объединил.

Пользователь: Как работать с feedback?
Ассистент: Сохраняй только разрешённые обезличенные примеры, классифицируй ошибки, добавляй корректный ответ и проверяй, что feedback не содержит секретов.

Пользователь: Как не обучить плохому стилю?
Ассистент: Отделяй production-quality examples от антипримеров и явно маркируй bad code с исправлением.

Пользователь: Как использовать антипримеры?
Ассистент: Показывай ошибку и причину, затем качественную версию и тест; не смешивай плохой код с правильным ответом без разметки.

Пользователь: Что делать с устаревшим API?
Ассистент: Добавь версию и дату, не выдавай старый синтаксис как единственный вариант, проверь текущую документацию проекта.

Пользователь: Как привязать модель к проекту?
Ассистент: Дай ей безопасный контекст: README, public interfaces, schemas, tests and conventions. Не передавай `.env`, приватные истории и production secrets.

Пользователь: Что делать, если модель предлагает несуществующую функцию?
Ассистент: Проверь импорт и API, покажи traceback, добавь пример в корпус и заставь evaluation проверять доступность символов.

Пользователь: Как проверять imports?
Ассистент: `compileall` проверяет синтаксис, импортный smoke test проверяет загрузку, а статический аудит ловит отсутствующие ссылки. Все три проверки дополняют друг друга.

Пользователь: Как проверять circular import?
Ассистент: Запусти чистый import главного модуля и изучи traceback. Раздели общие типы и функции, если модулю приходится импортировать друг друга.

Пользователь: Как управлять зависимостями?
Ассистент: Отделяй runtime и training requirements, фиксируй версии при production, проверяй лицензии и запускай smoke test после установки.

Пользователь: Что важно в Docker?
Ассистент: Маленький образ, pinned dependencies, non-root user, healthcheck, timeout, отсутствие секретов в layers и явный volume для checkpoint.

Пользователь: Как деплоить inference?
Ассистент: Отдельный сервис, checkpoint в persistent storage или artifact, `/health`, auth, rate limit, timeout и fallback в Telegram-боте.

Пользователь: Как тестировать сетевой fallback?
Ассистент: Замокай timeout, 500, invalid JSON, empty text and slow response. Убедись, что бот возвращает безопасное сообщение и не выдаёт награду дважды.

Пользователь: Как не блокировать event loop?
Ассистент: Не запускай тяжёлое обучение внутри Telegram handler. Используй отдельный worker/process/service или `asyncio.to_thread` только для умеренной CPU работы.

Пользователь: Что делать с CPU inference?
Ассистент: Ограничь длину, concurrency и частоту; проверь latency и не допускай блокировки polling loop.

Пользователь: Как измерить latency?
Ассистент: Запиши time.monotonic до и после запроса, раздели cold start и warm request, измерь p50/p95 на фиксированных prompts.

Пользователь: Что такое cold start?
Ассистент: Время загрузки процесса, зависимостей и checkpoint до первой готовности. Он может быть намного больше обычного запроса.

Пользователь: Как уменьшить cold start?
Ассистент: Ленивая загрузка, меньший checkpoint, подходящий runtime и отдельный warm service; не жертвуй безопасностью ради секунд.

Пользователь: Как обрабатывать SIGTERM?
Ассистент: Сохраняй checkpoint или состояние безопасно, закрой server и connections, дождись задач и верни процесс с понятным кодом.

Пользователь: Как не потерять обучение?
Ассистент: Сохраняй периодические checkpoint-ы, best validation, optimizer state и журнал; проверяй загрузку каждого сохранения.

Пользователь: Что делать при нехватке RAM?
Ассистент: Уменьши batch, embedding, layers или block size, проверь swap, освободи ненужные процессы и не продолжай до OOM без сохранения.

Пользователь: Как выбирать block size?
Ассистент: Он должен покрывать нужный контекст, но увеличивает память и время attention квадратично. Для trial выбери небольшой размер и измерь.

Пользователь: Как выбирать embedding?
Ассистент: Он должен делиться на число heads. Большой embedding повышает capacity и память; увеличивай его после проверки corpus и pipeline.

Пользователь: Как проверять training speed?
Ассистент: Запиши steps/sec, время evaluation, RAM и device. Сравни параметры при одинаковом batch и block.

Пользователь: Как обучать только полезным ответам?
Ассистент: Увеличивай долю качественных instruction/answer pairs, проверяй формат и удаляй filler text, который не отражает целевую задачу.

Пользователь: Как сделать корпус разнообразным?
Ассистент: Включи разные языки программирования только при необходимости, разные уровни сложности, ошибки, тесты, объяснения и ограничения.

Пользователь: Что такое curriculum?
Ассистент: Постепенное усложнение: синтаксис и функции, затем async/DB/API, потом архитектура и debugging.

Пользователь: Как обучать code style?
Ассистент: Дай много последовательных примеров с одинаковыми conventions, форматированием и объяснением why, но сохраняй разные задачи.

Пользователь: Как не запутать модель инструкциями?
Ассистент: Используй явные markers и единый template, не смешивай комментарии автора с expected assistant answer без разделителей.

Пользователь: Как проверить delimiters?
Ассистент: Напиши parser, который находит пары `Пользователь:` и `Ассистент:` и сообщает о пропущенных или вложенных markers.

Пользователь: Что делать с пустыми примерами?
Ассистент: Удалять или заполнить, потому что они добавляют шум и нарушают структуру обучения.

Пользователь: Какой размер validation?
Ассистент: Часто 10–20 процентов для небольшого корпуса, но важнее независимость и покрытие, чем точный процент.

Пользователь: Как сравнивать checkpoint?
Ассистент: Один и тот же evaluation set, одинаковый decode temperature/top-k и таблица с loss, pass rate, latency и examples.

Пользователь: Что делать с плохим checkpoint?
Ассистент: Не подключать его к production, сохранить для анализа, выбрать лучший по validation или удалить после проверки артефактов.

Пользователь: Как завершить experiment report?
Ассистент: Укажи commit, data version, args, device, duration, loss curve, sample outputs, failures and decision.

Пользователь: Что нужно сообщить пользователю?
Ассистент: Что сделано, что проверено, что не проверено и какой следующий шаг. Не преувеличивай качество маленькой модели.

Пользователь: Напиши итог.
Ассистент: Pipeline готов, trial обучен, генерация проверена, качество пока экспериментальное, корпус нужно расширять, production AI не меняем.

Пользователь: Какой принцип качества модели?

Ассистент: Маленький шаг, понятная проверка, фиксированный результат и документированный следующий шаг.
